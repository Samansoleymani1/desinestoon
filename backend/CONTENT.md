# مدیریت محتوا — فاز سوم

پنل از همان حساب، نشست، CSRF و محدودیت ورود فاز دوم استفاده می‌کند. هیچ سیستم احراز هویت موازی وجود ندارد. سایت اصلی و گالری GitHub Pages هنوز از JavaScript ثابت استفاده می‌کنند؛ مدیریت محتوا در این فاز فقط دیتابیس و API را تغییر می‌دهد.

## ارتقای دیتابیس موجود

پس از پشتیبان‌گیری، migration یک‌باره فاز سوم را روی دیتابیس فاز دوم اجرا کنید:

```powershell
mysql -u root -p designestoon_db
```

داخل MySQL، مسیر واقعی مخزن را جایگزین کنید:

```sql
SOURCE C:/projects/desinestoon/backend/database/migrations/003_content_management.sql;
EXIT;
```

`projects.archived_at` برای بایگانی و ایندکس مربوط به نمایش عمومی اضافه می‌شود. `media.byte_size` حجم فایل جدید را نگهداری می‌کند؛ برای تصاویر قبلی مقدار NULL معتبر است. migration هیچ رکورد یا فایل اولیه‌ای را حذف یا جابه‌جا نمی‌کند. آن را دوباره اجرا نکنید؛ DDL در MySQL تراکنشی نیست. نصب تازه فقط از schema.sql به‌روز استفاده می‌کند؛ روی دیتابیس فاز اول ابتدا migration 002 و بعد 003 اجرا شوند. اجرای schema با IF NOT EXISTS جایگزین migration نیست.

## پیش‌نیاز و اجرای ویندوز

PHP 8.2+ با افزونه‌های `pdo_mysql`، `fileinfo` و `gd`، و MySQL 8.0.16+ لازم است. GD باید JPEG، PNG و WebP را بخواند؛ برای خروجی WebP به پشتیبانی WebP در GD نیاز است. در نبود encoder WebP، خروجی JPEG/PNG بازرمزگذاری‌شده استفاده می‌شود. GD غیرفعال باعث شکست امن آپلود می‌شود؛ فایل خام ذخیره نخواهد شد.

از ریشه مخزن:

```powershell
php -m | Select-String 'PDO|pdo_mysql|fileinfo|gd'
php -r "print_r(gd_info());"
New-Item -ItemType Directory -Force backend/storage/uploads
php -d upload_max_filesize=10M -d post_max_size=12M -d memory_limit=256M -d display_errors=0 -S 127.0.0.1:8080 -t backend/public
```

مسیر `/admin/login.php` را در مرورگر سرویس محلی باز کنید. ساخت حساب اولیه و تنظیم اتصال طبق ADMIN.md انجام می‌شود؛ حساب مدیر موجود تغییر نمی‌کند. پردازش PHP باید اجازه نوشتن در `backend/storage/uploads` داشته باشد، اما کد برنامه نباید در محیط عملیاتی قابل نوشتن باشد.

در `php.ini` هاست نیز این محدودیت‌ها اعمال شوند:

```ini
upload_max_filesize=10M
post_max_size=12M
memory_limit=256M
max_file_uploads=1
display_errors=Off
```

`.user.ini` در public برای FPM/CGI آماده شده است؛ اعمال آن وابسته به تنظیم هاست است و سرور داخلی PHP آن را نمی‌خواند. در وب‌سرور نیز سقف بدنه حداقل ۱۲ مگابایت برای فرم تک‌تصویری تنظیم شود. سقف واقعی تصویر در کد همیشه ۱۰٬۴۸۵٬۷۶۰ بایت است؛ افزایش php.ini این سقف را دور نمی‌زند. در Apache دسترسی به فایل‌های dotfile را ببندید؛ در Nginx نیز مسیر فایل‌های مخفی را deny کنید. ریشه عمومی فقط `backend/public` باشد و HTTPS طبق ADMIN.md اجباری است.

## مجوز حساب وب

به حساب وب مجوز مدیریت ساختار یا تغییر admins ندهید. نمونه برای حساب موجود:

```sql
GRANT SELECT ON designestoon_db.admins TO 'designestoon_app'@'127.0.0.1';
GRANT SELECT, UPDATE ON designestoon_db.admin_login_limits TO 'designestoon_app'@'127.0.0.1';
GRANT SELECT, INSERT, UPDATE ON designestoon_db.projects TO 'designestoon_app'@'127.0.0.1';
GRANT SELECT, INSERT, UPDATE, DELETE ON designestoon_db.categories TO 'designestoon_app'@'127.0.0.1';
GRANT SELECT, INSERT ON designestoon_db.media TO 'designestoon_app'@'127.0.0.1';
GRANT SELECT, INSERT, UPDATE ON designestoon_db.settings TO 'designestoon_app'@'127.0.0.1';
```

مجوز DELETE برای projects یا media لازم نیست. GRANT محدود، مجوز گسترده قبلی را لغو نمی‌کند؛ حساب‌های قدیمی را بازبینی کنید. حساب جداگانه API عمومی فقط به SELECT روی categories، projects، media و settings نیاز دارد. ساخت مدیر با حساب CLI دارای INSERT روی admins انجام شود.

## عملیات پنل

- نمونه‌کار: افزودن تصویر و عنوان، دسته، ترتیب و انتشار؛ ویرایش بدون انتخاب فایل، تصویر قبلی را حفظ می‌کند. عدد ترتیب کوچک‌تر زودتر نمایش داده می‌شود و تساوی با id مرتب می‌شود.
- بایگانی: تأیید checkbox لازم است؛ رکورد باقی می‌ماند و از API خارج می‌شود. بازیابی نیز تأیید می‌خواهد و همیشه منتشرنشده است. برای انتشار دوباره، فرم ویرایش را ذخیره کنید. رکورد بایگانی‌شده تا زمان بازیابی قابل ویرایش نیست.
- دسته: افزودن slug لاتین یکتا؛ عنوان، ترتیب و فعال‌بودن قابل تغییرند. slug تمام دسته‌های موجود در سرور ثابت است، حتی اگر درخواست دست‌کاری شود. `all` رزرو شده است. حذف فقط با تأیید و بدون هیچ نمونه‌کار وابسته، حتی بایگانی‌شده، مجاز است.
- تماس: شماره اصلی اجباری است، شماره دوم اختیاری؛ ارقام فارسی/عربی و شکل +98 پذیرفته و به ۱۱ رقم استاندارد ایران تبدیل می‌شوند. اینستاگرام فقط URL معتبر HTTPS صفحه Instagram است. ذخیره سه تنظیم تراکنشی است. شماره پیش‌فرض `09117901519` تا ثبت مقدار جدید باقی می‌ماند.
- تمام نوشتن‌ها POST، احراز هویت و CSRF دارند. پیام موفقیت فقط پس از ذخیره موفق و redirect نمایش داده می‌شود؛ خطای اعتبارسنجی داده موجود را تغییر نمی‌دهد. جزئیات SQL، مسیر داخلی و رمز در پاسخ منتشر نمی‌شوند.

## فایل‌ها و سیاست نگهداری

فایل جدید ابتدا از نظر اندازه واقعی، پسوند، MIME تشخیص‌داده‌شده با Fileinfo، ابعاد و امکان decode با GD بررسی می‌شود. هر ضلع حداکثر ۸۱۹۲ و مجموع تصویر حداکثر ۱۶ میلیون پیکسل است تا مصرف حافظه محدود بماند. نام فرستاده‌شده کاربر هرگز به مسیر ذخیره تبدیل نمی‌شود. تصویر با نام تصادفی ۱۲۸ بیتی بازرمزگذاری می‌شود؛ metadata و کد افزوده به فایل خام منتقل نمی‌شوند. WebP با کیفیت ۸۵، یا JPEG با کیفیت ۹۰ / PNG استفاده می‌شود. انیمیشن و metadata اصلی حفظ نمی‌شوند؛ گردش تصویر براساس EXIF در این نسخه انجام نمی‌شود.

فایل‌های نهایی در `backend/storage/uploads`، بیرون public و خارج از Git هستند. مسیر ثبت‌شده در media مانند `/media.php?file=<random>.webp` است؛ endpoint تصویر فقط برای نمونه‌کار منتشرشده و بایگانی‌نشده در دسته فعال پاسخ می‌دهد. پیش‌نمایش مدیر از `/admin/image.php?id=<media-id>` با نشست معتبر است. هیچ فایل آپلودشده‌ای به‌عنوان PHP اجرا نمی‌شود و هیچ پوشه آپلودی در document root نیست. مسیرهای فایل از الگوهای محدود خوانده می‌شوند، نه از ورودی مسیر دلخواه.

در تعویض تصویر، فایل و رکورد media قبلی نگهداری می‌شوند. هیچ حذف خودکار رسانه قدیمی یا تصویر اولیه وجود ندارد. بایگانی نیز فایل را حذف نمی‌کند. در خطای معمول ذخیره، تراکنش rollback و فایل تازه پاک می‌شود؛ فایل `.part` در finally پاک می‌شود. فایل‌سیستم و MySQL یک تراکنش مشترک ندارند: در قطع برق/kill ناگهانی ممکن است فایل بدون مرجع باقی بماند. ابزار `scripts/audit-uploads.php` برای شناسایی این موارد فقط گزارش می‌دهد و هیچ فایل را حذف نمی‌کند. حذف دستی فقط پس از پشتیبان‌گیری، بررسی توقف آپلودهای هم‌زمان و تأیید سیاست نگهداری انجام شود؛ فایل دارای رکورد media حتی اگر فعلاً استفاده نشود، رسانه نگهداری‌شده است و orphan محسوب نمی‌شود.

برای انتقال به هاست، دیتابیس و کل `storage/uploads` را با هم منتقل و مجوزها را تنظیم کنید. مسیر فایل از مسیر فیزیکی ویندوز مستقل است. لینک API برای تصاویر جدید نسبت به origin Backend است؛ در فاز چهارم اگر سایت و Backend دامنه متفاوت داشته باشند، باید origin Backend به `/media.php?...` اضافه شود. تصاویر اولیه `./assets/images/...` همچنان نسبت به سایت اصلی هستند و هیچ تغییری نکرده‌اند.

## API عمومی

- `GET /api/projects.php`: قالب شش‌فیلدی سابق؛ فقط منتشرشده، بدون بایگانی، با دسته فعال.
- `GET /api/categories.php`: فقط دسته‌های فعال.
- `GET /api/contact.php`: فقط سه کلید عمومی مجاز، بدون هیچ تنظیم خصوصی:

```json
{"contact_phone_primary":"09117901519","contact_phone_secondary":"09366208359","contact_instagram":"https://www.instagram.com/designestoon_amol/"}
```

- `GET /media.php?file=<random>.webp`: فقط تصویر مورد استفاده محتوای عمومی مجاز؛ draft، بایگانی، فایل بدون مرجع و مسیر دست‌کاری‌شده 404 می‌گیرند. لغو انتشار نمی‌تواند نسخه‌ای را که قبلاً کاربر دانلود کرده پاک کند.

همه مسیرهای عمومی فقط GET دارند. API و پنل هیچ CORS عمومی اضافه نکرده‌اند؛ اتصال cross-origin در فاز چهارم باید با origin مشخص طراحی شود.

## آزمون‌های واقعی

روی دیتابیس جداگانه `designestoon_test` با schema جدید و داده Seed اجرا کنید. تست فاز اول به دیتابیس خالی نیاز دارد و خودش Seed می‌کند؛ سپس به‌ترتیب:

```powershell
node backend/tests/source.test.js
php backend/tests/integration.php
php backend/tests/auth-integration.php
php -d memory_limit=256M backend/tests/content-integration.php
```

همه تست‌های PHP فقط نام دیتابیس تست را می‌پذیرند. پورت‌های ۱۸۰۸۱ تا ۱۸۰۸۳ آزاد باشند. تست محتوا از ارسال واقعی multipart استفاده می‌کند و فایل JPEG/PNG/WebP، فایل بیش از ۱۰ مگابایت، PHP تغییرنام‌یافته، تصویر خراب و تصویر معتبر با payload اضافی را بررسی می‌کند. داده‌ها و فایل‌های ساخته‌شده تست پس از پایان پاک می‌شوند. تست محتوا به ۲۲ نمونه‌کار، هفت دسته و جدول admins خالی نیاز دارد؛ روی دیتابیس/فضای ذخیره عملیاتی اجرا نشود. دستورهای تنظیم محیط تست در README هستند.

## فاز چهارم

اتصال لایه داده گالری به API، نگاشت مبنای URL تصاویر قدیمی و جدید، دسته‌های پویا، استفاده از تماس ذخیره‌شده در باکس رزرو/فوتر، حالت استاتیک پشتیبان، مدیریت خطای شبکه و در صورت نیاز CORS محدود باقی مانده‌اند. HTML/CSS/JavaScript سایت عمومی در این فاز تغییر نکرده‌اند. رابط بازیابی رمز مدیر و مدیریت تاریخچه رسانه نیز هنوز وجود ندارد.
